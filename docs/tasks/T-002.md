# Задача T-002: Закрыть критические уязвимости до production
Модель: GPT-5.6 Sol, high — задача затрагивает tenant isolation, публичный HTML, файлы, ограничения ресурсов и совместимое обновление runtime-зависимостей.

## Контекст

Onay Mebel хранит проекты, пользовательские каталоги и настройки мебельных компаний, рассчитывает изделия и публикует коммерческие предложения. T-001 принята и установила, что текущий коммит нельзя открывать в production: найдены четыре критических класса проблем и применимые уязвимости runtime-зависимостей. Прочитай `docs/product.md` полностью, `docs/tech.md` и `docs/reports/T-001.md`; технические утверждения аудита перепроверь по коду перед исправлением.

Production будет запускаться с чистой PostgreSQL и пустым uploads на VPS 2 CPU / 2 ГБ RAM / 40 ГБ. Основной сценарий публичного КП и публичная выдача изображений должны сохраниться, при этом пользователь может изменять и удалять только свои данные.

## Что нужно получить

Закрыть критические уязвимости, перечисленные в T-001, чтобы дальнейшая работа над production-конфигурацией опиралась на безопасные границы данных и ввода. После задачи попытки одного пользователя изменить компоненты или удалить файлы другого должны отклоняться; данные КП не должны исполняться как произвольный HTML/JavaScript; чрезмерные запросы и загрузки должны предсказуемо отклоняться до исчерпания памяти или диска; применимые runtime-зависимости не должны оставаться заведомо уязвимыми без проверенного обоснования.

## Границы

Входит:

- серверная tenant isolation для всех восьми наборов компонентов изделия при массовом создании/обновлении, включая переданные ID компонентов и доступность custom material/hardware для текущего пользователя;
- ownership загруженных файлов и авторизация удаления; публичное чтение изображений, нужное для КП, сохраняется;
- защита генерации и показа публичного КП от HTML/script/attribute/URL injection во всех контекстах, а также безопасная изоляция документа в браузере без потери просмотра, печати и скачивания;
- согласованные конечные лимиты nginx/backend/multipart, DTO и вложенных структур, строк, массивов, изображений и хранения uploads с корректными ответами 400/413 и без падения процесса;
- минимальные совместимые обновления только тех runtime-зависимостей, чьи advisories применимы к используемым публичным путям; обновлённые lock-файлы и повторный аудит корня, backend и frontend;
- регрессионные тесты для найденных атак, проверки сборки, TypeScript, ESLint и полного существующего набора тестов; устранение текущих ESLint errors, при этом существующее количество backend warnings не увеличивать;
- миграция Prisma и обновление `.env.example`/production-конфигурации, если это требуется выбранному решению; актуализация `docs/tech.md`.

Не входит: подключение к VPS, Dokploy и деплой; настройка backup; исправление seed/bootstrap, актуальности роли JWT и отзыва access-сессий, trust proxy/rate limit, Telegram/clck.ru timeout, логов и SMS reset; выбор бизнес-часового пояса; изменение срока жизни публичной ссылки; общая переработка расчётной модели, UI или архитектуры; автоматическое `npm audit fix --force` и обновление зависимостей, не относящихся к найденным production-рискам.

## Критерии приёмки

- Негативные тесты с двумя пользователями доказывают, что нельзя обновить ни один из восьми типов компонентов чужого изделия через подстановку ID; чужие и неизвестные ID не превращаются в новые записи и не раскрывают чужие данные.
- Сервер проверяет, что выбранные custom material/hardware доступны текущему пользователю; общие позиции продолжают работать по действующим правилам каталога.
- У upload есть проверяемый владелец или эквивалентная серверная связь. Удаление чужого файла отклоняется, удаление своего работает, публичное отображение изображения в КП работает. Проверены неверные URL/path traversal и рассинхронизация БД/файловой системы.
- Тестовые payload с `</script>`, HTML-атрибутами, event handlers и опасными URL остаются текстом/отклоняются по контексту и не исполняются в публичном и внутреннем просмотре КП. Обычный русско- и казахоязычный контент, логотип, печать и скачивание продолжают работать.
- Для JSON, snapshot, массивов/строк компонентов, multipart-изображений и общего хранения uploads заданы конечные обоснованные лимиты, совместимые с VPS 2 ГБ. Oversize-запросы получают 400/413, не создают частичных данных/файлов и покрыты тестами.
- `npm audit` выполнен отдельно для корня, backend и frontend, включая `--omit=dev`. В production-графе не остаётся применимой critical/high уязвимости в затронутых публичных путях; каждое оставшееся critical/high finding классифицировано по применимости с advisory и причиной, почему его нельзя или не нужно исправлять в этой задаче.
- Backend и frontend собираются; TypeScript проходит; backend unit/e2e и новые security-регрессии проходят. Backend ESLint завершается без errors и не увеличивает baseline 789 warnings; frontend ESLint завершается без errors.
- Prisma schema/migrations проходят validate, а новая миграция при наличии проверена на чистой PostgreSQL и повторным `migrate deploy`; если локальный runtime объективно недоступен, точная причина и обязательный gate для T-006 зафиксированы без выдуманного результата.
- Секреты не попали в код, логи, тестовые фикстуры и Git. `git diff` не содержит изменений вне объёма задачи, временные артефакты удалены, `docs/tech.md` отражает новые границы и команды.

## Ограничения и требования

- Сохрани текущий стек и пользовательский сценарий из `docs/product.md`; не добавляй новые продуктовые функции.
- Все решения по HTML, iframe sandbox, загрузкам, Nest/Express limits, Prisma и обновляемым зависимостям сверяй с актуальной официальной документацией и security advisories. Не полагайся на память и не применяй массовые обновления без проверки совместимости.
- Проверки ownership выполняются на сервере для каждого действия. Ответы не должны позволять отличить существующий чужой объект от отсутствующего, если это не требуется текущим API.
- Лимиты должны действовать на самом раннем практичном слое и согласовываться между nginx и backend. Не ограничивай только интерфейс.
- Любое изменение схемы оформляется миграцией; проект разворачивается с чистой базой, но история миграций должна оставаться воспроизводимой.
- Не использовать реальные production-секреты и не подключаться к VPS.
