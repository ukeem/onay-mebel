# Задача T-004 [fix]: Исправить находки независимого review T-003
Модель: GPT-5.6 Sol, high — задача закрывает критический DoS по памяти, целостность файлового хранения и воспроизводимость production image.

## Контекст

T-003 независимо проверила T-002. Tenant isolation восьми component endpoints, доступ к custom-каталогу, контекстное экранирование КП, CSP/sandbox и ранние входные лимиты подтверждены. Однако production всё ещё закрыт тремя классами находок. Прочитай `docs/product.md`, `docs/tech.md`, `docs/tasks/T-002.md`, `docs/reports/T-002.md` и `docs/reports/T-003.md`; каждую находку перепроверь по коду до изменения.

Система будет работать на VPS 2 CPU / 2 ГБ RAM / 40 ГБ с чистой PostgreSQL и пустым uploads. Публичная ссылка КП, изображения, русский/казахский текст, печать и скачивание HTML должны сохраниться.

## Что нужно получить

Закрыть критическое раздувание памяти/HTML при генерации КП, сделать dependency graph финального backend image воспроизводимым и production-only, обеспечить восстановимую согласованность uploads между БД, квотами и файловой системой, а также добавить регрессионные доказательства для исправленных сценариев.

## Границы

Входит:

- переработка загрузки локальных изображений для КП так, чтобы один файл не читался/кодировался повторно, общий объём файлов и итогового HTML имели конечные безопасные пределы, а публичный запрос не блокировал event loop синхронным чтением большого набора файлов;
- безопасное поведение при превышении лимита: предсказуемый bounded ответ или контролируемая деградация изображений без генерации огромной строки; обычное КП с несколькими изображениями остаётся полностью рабочим и скачиваемым;
- исправление backend Dockerfile/runtime layout: Prisma CLI и `@prisma/client` одной закреплённой совместимой версии, повторяемая установка по lock-файлу, отсутствие Jest/ts-jest/Handlebars/@nestjs/cli и иных devDependencies в финальном runtime; миграции и seed перед стартом сохраняются либо переносятся в явный migration stage/service без открытия нового публичного сервиса;
- crash-consistent upload lifecycle или эквивалентная восстанавливаемая схема: после сбоя между БД и ФС следующая безопасная reconciliation приводит metadata, user/global counters и фактические файлы к согласованному состоянию; временные и orphan-файлы не копятся;
- удаление пользователя очищает его физические uploads и корректно обновляет общий счётчик; ошибка ФС не должна незаметно удалить metadata/владельца и оставить неконтролируемый мусор;
- защита reconciliation от traversal/symlink и удаление только канонических файлов внутри `UPLOAD_DIR`; многократный запуск идемпотентен;
- регрессии для memory amplification, повторных ссылок на одно изображение, общего output/image budget, ошибок чтения, crash/reconciliation, удаления пользователя и фактического runtime dependency graph; усилить snapshot boundary tests (bytes/nodes/object keys/NaN) и urlencoded limits;
- актуализация `docs/tech.md` по фактическому lifecycle, лимитам, Docker graph и deployment gates.

Не входит: подключение к VPS/Dokploy; реальный production deploy; исправление seed/bootstrap, JWT/session, trust proxy/rate limit, внешних timeout/логов/SMS; изменение срока публичной ссылки; общая переработка расчётов или UI. Полный browser-level и реальный PostgreSQL two-tenant smoke допустимо оставить обязательным gate T-006, если локальный Linux/PostgreSQL runtime объективно недоступен; точный сценарий тогда зафиксировать в отчёте и `docs/tech.md`.

## Критерии приёмки

- Тест из T-003 с 20 повторными ссылками на один файл 1 МиБ больше не создаёт HTML около 28 МиБ и heap amplification около 68 МиБ. Один уникальный файл читается/кодируется максимум один раз на генерацию, а число ссылок не умножает base64 payload линейно.
- Для совокупности уникальных изображений и итогового HTML действует обоснованный конечный бюджет, безопасный для VPS 2 ГБ. Пограничные и превышающие тесты доказывают bounded память/ответ; публичный и внутренний endpoints ведут себя одинаково безопасно.
- Обычное КП с несколькими локальными WebP, русским/казахским текстом, тарифами, печатью и скачиванием остаётся рабочим. XSS/CSP/sandbox регрессии T-002 продолжают проходить.
- Точное воспроизведение Docker install/build показывает совпадающие закреплённые версии Prisma CLI/client и отсутствие devDependencies в финальном runtime. Audit фактического runtime tree не содержит применимой critical/high, либо каждое оставшееся finding классифицировано по реально присутствующему графу.
- Reconciliation на искусственных состояниях «metadata без файла», «файл без metadata», неверные counters и временный файл восстанавливает согласованность идемпотентно; не выходит за `UPLOAD_DIR` и не следует опасным symlink.
- Удаление пользователя с uploads не оставляет файлов и не завышает global counter. При ошибке удаления результат остаётся восстановимым и явно сигнализируется.
- Backend unit/security/e2e, frontend проверки, Prisma validate/diff, TypeScript, build и линтеры проходят без новых errors; новый код покрыт meaningful tests. Реальные Docker/PostgreSQL проверки выполнить, если runtime доступен; иначе не выдумывать результат и сохранить точный T-006 gate.
- В Git нет секретов и временных артефактов; изменения ограничены находками T-003, `docs/tech.md` и отчётом.

## Требования к решениям

- Сверяй Node/Nest streaming/async FS, npm install/omit semantics, Docker multi-stage, Prisma deployment и filesystem consistency с актуальной официальной документацией.
- Не исправляй проблему уменьшением только frontend/UI лимита: сервер и публичный endpoint должны быть безопасны для сохранённых или специально сформированных данных.
- Не удаляй произвольные файлы по данным из БД без повторной проверки канонического имени и resolved path.
- Не используй `npm audit fix --force` и не обновляй зависимости вне необходимости этой задачи.
- Не подключайся к VPS и не используй production-секреты.
