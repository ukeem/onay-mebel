# Отчёт T-001: Аудит проекта и готовности к чистому production-деплою

**Статус:** готово

## Что сделано

Проверен исходный коммит `a6cc70c` на `dev`, исходное рабочее дерево чистое. Полностью прочитан docs/product.md, изучены frontend/backend, Prisma, все 24 SQL-миграции, seed, Compose, Dockerfile, nginx и удалённые инструкции из Git.

**Вывод: текущий коммит безопасно открывать в production нельзя. T-002 обязательна до деплоя.** Чистая база устраняет необходимость переноса данных, но не устраняет нарушения изоляции, HTML injection, уязвимые зависимости и риски отказа на 2 ГБ RAM.

Заполнен docs/tech.md: версии из lock, структура, команды, conventions, auth/data flow, env, инфраструктура, seed, проблемы и предварительный ресурсный бюджет. Код и production-конфигурация не изменены.

### Критично

1. **Изменение чужих компонентов.** products.service.ts:132–515: после ensureProductOwner(productId) все восемь upsert-методов обновляют существующие записи по `where: {id: item.id}`, без проверки их productId. Зная чужой ID, пользователь может изменить чужую запись и получить её в ответе. Вызов собранного ProductsService с mock Prisma подтвердил: для собственного изделия отправленный victim-section дошёл до update без productId. Это проверка пути кода, не атака на реальную БД. Исправить весь набор компонентов и проверять доступность переданных material/hardware ID для текущего пользователя; неизвестные чужие ID не считать новыми записями.
2. **Удаление чужих uploads.** uploads.controller.ts:38 и uploads.service.ts:115: DELETE принимает URL, но не owner; любой вошедший пользователь с известным публичным URL удалит чужое изображение/логотип. Проверка basename защищает путь, но не права. Нужна связь upload→owner и серверная проверка удаления; выдача публичных изображений для КП допустима по сценарию.
3. **Stored HTML/script injection в публичном КП.** calculations.service.ts:1831–1842, 1921–1937 и другие шаблонные вставки не экранируют name/description/project/clientData; JSON.stringify внутри script не экранирует закрывающий script-тег. Вызов собранного generateProposal с безопасным маркером `</script><script>window.auditMarker=1</script>` сохранил его в HTML 4 раза. Оба frontend public page.tsx создают Blob и iframe с allow-scripts+allow-same-origin; frontend CSP допускает inline scripts. Helmet исходного fetch-ответа не является достаточной защитой созданного Blob. Возможны действия от лица вошедшего посетителя на том же origin; httpOnly cookies не предотвращают same-origin запросы. Браузерная эксплуатация не проводилась. Нужны контекстное экранирование HTML/атрибутов/JS, проверка URL и безопасная изоляция КП с сохранением функциональности.
4. **Риск отказа по памяти/диску.** nginx/default.conf: client_max_body_size 0; main.ts: BODY_LIMIT default 1024mb, парсинг до auth; snapshot DTO проверяет только IsObject. Строки/массивы компонентов почти без верхних границ, upload 50 MiB буферизуется, квот хранения нет. JSON может иметь несколько копий в памяти; один запрос способен превысить бюджет VPS. Нужны согласованные конечные лимиты nginx/backend/multipart, структуры snapshot, массивов/строк, изображений и хранения; ответы 413/400 без падения. BODY_LIMIT сейчас не передаётся Compose, одного значения в UI Dokploy недостаточно.

### Важно

5. **Уязвимые зависимости.** Полный и omit=dev audit выполнены; подробности ниже. Next App Router, Multer, sharp, compression и WS обслуживают пользовательские запросы — их нельзя считать только dev-риском.
6. **Seed не fail-closed и меняет данные при каждом старте.** Выполняется до Joi; при отсутствующих env использует встроенный пароль/телефон. Existing admin не обновляется. Seed перезаписывает moduleTypes всех пользователей и копирует SUPER custom-каталоги без userId=null. Не транзакционен. Нужны обязательная проверка bootstrap env до записи, отсутствие default credentials, однократный/безопасный bootstrap и проверка повторного запуска без изменения пользовательских настроек.
7. **Устаревающие права и access после reset.** JwtStrategy читает из БД только status/activeUntil, роль берёт из JWT. Пониженный ADMIN сохраняет прежнюю роль до истечения access; пароль/reset удаляет refresh, но access работает до 15 минут. Force-logout лишь сигнал браузеру. Нужны актуальная роль и серверный отзыв access при смене пароля/прав; тесты с прежним токеном. Refresh rotation delete+issue не атомарна, race допускает повторную выдачу; хранение refresh в открытом виде усиливает последствия утечки БД.
8. **Rate limit за proxy.** trust proxy/getTracker отсутствуют: Nest видит nginx IP, пользователи делят общий лимит 100/min, login 5/min. При включении доверия нельзя доверять произвольному X-Forwarded-For: настроить проверяемую цепочку Traefik→nginx→backend. Throttler in-memory, после restart сбрасывается; WS connection/message limits отдельно не заданы.
9. **Внешние запросы/логи.** Telegram и публичный clck.ru fetch без timeout и ограничения response body; shorten не ограничивает длину/схему/назначение URL. Адрес fetch фиксирован, прямой произвольный server-side fetch не обнаружен; это не доказанная SSRF. Нужны timeout, cap, обработка ошибок и ограничение использования shorten. Notify/SMS/auth логируют номера, Telegram failure может включать внешние детали; убрать персональные данные/потенциальные token URL из логов. SMS — заглушка: production reset сообщает об отправке, но SMS не приходит. Мозгу решить: отключить недействующий reset либо отдельная интеграция; поставщик в аудите не выбирался.
10. **Readiness/сети/восстановление не подтверждены.** Нет backend/frontend/nginx healthcheck, degraded health возвращает HTTP 200. depends_on после PostgreSQL только порядок старта. Нужны проверяемая readiness и поведение при рестартах; private network + доступ nginx к Traefik проверить через Dokploy Preview Compose. Внешних backups и restore-процедуры нет.
11. **Проверки качества красные.** Backend ESLint 1 error/789 warnings, frontend 10 errors. Backend start:prod указывает dist/main, фактическая сборка dist/src/main.js; Docker CMD корректен. Docker после prune повторно устанавливает Prisma: финальное дерево нуждается в отдельной проверке воспроизводимости и аудите.

## Что не сделано и почему

Ничего из найденного не исправлено согласно границам аудита. VPS/Dokploy не подключались, деплой не выполнялся.

Не выполнены реальные PostgreSQL migrate deploy/seed/reseed/schema drift и Docker image build/run: docker info не находит Docker Desktop Linux daemon (npipe dockerDesktopLinuxEngine отсутствует), psql не установлен. docker compose config прошёл, но это не подтверждение запуска. Не снимались RSS/диск на VPS и не выполнялся браузерный end-to-end от регистрации до КП; такие проверки остаются gates T-003. Отсутствие БД не мешало единственному smoke e2e: он не делает полезных запросов к данным.

## Технические решения

Сохранён существующий стек; новые библиотеки/обновления не устанавливались в зависимости проекта. Установлены только lock-зависимости для проверок, исходные lock не изменены. Источники сверены на дату аудита:

- [Dokploy installation](https://docs.dokploy.com/docs/core/installation): Ubuntu 24.04 поддерживается, минимум панели 2 GB RAM/30 GB disk; это не гарантия вместимости приложения.
- [Dokploy Compose Domains](https://docs.dokploy.com/docs/core/docker-compose/domains): UI добавляет labels/networks; без isolated deployment присоединение выбранного nginx к dokploy-network требует проверки связности остальных сервисов. Нужен Preview Compose, домены в nginx:80; БД не публиковать.
- [Docker startup order](https://docs.docker.com/compose/how-tos/startup-order): старт контейнера не равен готовности. [Resource constraints](https://docs.docker.com/engine/containers/resource_constraints/) и [Compose services](https://docs.docker.com/reference/compose-file/services/): ограничения RAM/swap задаются явно; текущий Compose их не задаёт.
- [Node releases](https://nodejs.org/en/about/previous-releases): Node 22 поддерживаемый LTS; удалённый CI Node 20 устарел. [Prisma 7 requirements](https://www.prisma.io/docs/orm/v7/reference/system-requirements): Node ^22.12, ^24 совместимы; использовать документацию именно v7, не новые команды v8. [Seeding v7](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/seeding): seed — явный отдельный шаг, здесь его запускает CMD.
- [Next self-hosting](https://nextjs.org/docs/app/guides/self-hosting), [memory](https://nextjs.org/docs/app/guides/memory-usage): reverse proxy и контроль ресурсов; Webpack-only оптимизации нельзя автоматически переносить на текущий Turbopack.
- [Nest throttler/proxy](https://docs.nestjs.com/security/rate-limiting): клиентский IP требует корректной настройки доверенного proxy.
- [PostgreSQL 16 memory](https://www.postgresql.org/docs/16/runtime-config-resource.html), [backup](https://www.postgresql.org/docs/16/backup.html): work_mem умножается на операции/соединения, backups должны быть согласованными. [Ubuntu memory protections](https://documentation.ubuntu.com/security/security-features/process-memory/): swap учитывает требования защиты хранимых данных; сервер не проверялся.

История: прочитаны три удалённых файла `.github` из родителя `50a8984`. Подтверждены data flow, modules, cookies, DTO, i18n, standalone и proxy. Отвергнуты устаревшие утверждения: uploads 5 MB (сейчас 50), полностью безопасный idempotent seed, всегда корректный ownership, отсутствие NEXT_PUBLIC env (теперь цены), наличие HSTS в Next headers. Старый CI использовал --fix и Node 20, деплой по push main; это исторические инструкции, не текущий workflow.

`npm audit --package-lock-only --json`, каждый каталог отдельно; исходный exit=1 при находках. Подсчёт означает уязвимые package entries с meta-vulnerabilities, не число CVE/доказанных exploit.

Корень: concurrently→shell-quote; только developer commands с фиксированными строками, в runtime Docker корня нет. Backend critical handlebars — tooling, proxy-addr — runtime, но advisory о trusted mapped subnet требует соответствующей proxy-конфигурации; текущее отсутствие trust proxy не доказывает эксплуатацию. Prisma CLI/Hono присутствуют в графе и CLI возвращается в runtime image, но приложение не запускает Hono server. Joi сейчас валидирует конфигурацию, не публичные рекурсивные схемы. Nest/path-to-regexp route-specific advisory требует анализа шаблонов, не все URL обязательно уязвимы.

Наиболее применимые: [Multer uncontrolled recursion](https://github.com/expressjs/multer/security/advisories/GHSA-5528-5vmv-3xc2) и другие multipart DoS из audit; [Next Server Components DoS](https://github.com/vercel/next.js/security/advisories/GHSA-h25m-26qc-wcjf) — используется App Router; sharp обрабатывает недоверенные изображения, compression/WS доступны в runtime. Next Windows RCE не относится к Linux, Image Optimization findings частично неприменимы при unoptimized=true. Axios в основном browser-side с относительными URL: Node proxy/SSRF findings не становятся доказанной серверной SSRF. next-intl redirect/precompile зависят от включения соответствующих функций. Dev ESLint/shadcn/Jest findings не приравнивать к публичным эндпоинтам. Исправления выбирать по реальному patched range и повторному audit; audit предлагал Next 16.4.2 и sharp 0.35.5, это не проверенные здесь обновления. Не применять audit fix --force вслепую.

### Ресурсы и T-003

Предварительный runtime бюджет: OS+Docker+Dokploy/его PostgreSQL/Redis+Traefik 650–950 MiB, app PostgreSQL 200–350, backend 200–350, frontend 150–300, nginx 10–30. Итого примерно 1.2–2.0 GiB до пиков. На 2 GiB запас мал, гарантии нагрузки нет.

Минимальный план: swap 4 GiB с 0600/fstab и проверкой reboot, swappiness=10; один build/deployment одновременно, backend/frontend последовательно, предпочтительно образы собирать вне VPS. На Next build планировать ещё 1–2+ GiB transient, runtime mem_limit BuildKit не ограничивает. Начальные лимиты для испытаний: PostgreSQL/backend/frontend/nginx 384/384/320/64 MiB, V8 backend/frontend 256/192 MiB; проверить seed/миграции под теми же лимитами. PostgreSQL shared_buffers 64–128 MiB, work_mem 2–4 MiB, connections 20–30, app pool 5–10. Это стартовые значения для замеров, не внесённая конфигурация.

Контроль docker stats/free/vmstat/OOMKilled/memory.events, latency/5xx, df/docker system df. Перед сборкой ≥8 GiB free disk и ≥300 MiB MemAvailable, alert RAM 80%, disk 75%/90%; sustained swap/OOM — запрет публичного запуска. Диск 40 GB: 4 GiB swap, ~6–10 OS/панель, ~4–8 images, ~3–8 build cache, данные/WAL плюс ≥8 GiB резерва; верхние оценки не помещаются, нужны квоты/очистка. Логи 10m×3; после успешного релиза проверить system df и чистить builder cache старше 168h, сохраняя rollback image и все data volumes. Ежедневные внешние pg_dump+uploads, retention 7 daily/4 weekly как предложение, restore в отдельное окружение; live pgdata tar не считать backup.
