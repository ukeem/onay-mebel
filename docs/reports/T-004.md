# Отчёт T-004: Исправление блокирующих находок review T-003

**Статус:** готово

## Что сделано

- Закрыто раздувание памяти и HTML при генерации КП. Локальные изображения теперь собираются только из реально отображаемых тарифов и деталей, читаются асинхронно и последовательно, а каждый уникальный канонический `/uploads/<uuid>.webp` читается и кодируется не более одного раза за генерацию.
- Base64 каждого уникального изображения помещается в HTML один раз и повторно используется всеми ссылками через `data-proposal-image`. Регрессия с 20 ссылками на файл 1 MiB создаёт один payload, выполняет один `lstat` и один `readFile`, а размер ответа остаётся меньше 2 MiB вместо примерно 28 MiB.
- Введены два серверных предела: 6 MiB суммарных исходных уникальных изображений и 10 MiB итогового UTF-8 HTML. Не помещающиеся, исчезнувшие или нечитаемые изображения контролируемо пропускаются; превышение конечного HTML возвращает `413`. Публичный и внутренний endpoints используют один и тот же защищённый service.
- Синхронные `existsSync/statSync/readFileSync` удалены из пути генерации КП. Обычный self-contained HTML, WebP, русский/казахский текст, тарифы, lightbox, печать и скачивание сохранены; XSS, CSP и iframe sandbox регрессии продолжают проходить.
- Усилена граница сохранённого calculation snapshot: ограничиваются UTF-8 bytes, глубина, число узлов, длина массивов, число ключей объекта и строк, отклоняются `NaN`/`Infinity`. E2E дополнительно доказывает раннее отклонение oversized JSON и urlencoded тела/числа параметров.
- Перестроен backend Dockerfile. Builder устанавливает полный locked graph и собирает приложение; независимый `production-deps` выполняет чистый `npm ci --omit=dev`, генерирует Prisma Client и проверяет граф; runner получает только build artifacts и production dependencies.
- `prisma` и `@prisma/client` закреплены одной точной версией `7.4.0`. Runtime использует локальный `./node_modules/.bin/prisma`, не допускает неявную загрузку через `npx`. Добавлен `scripts/verify-runtime-dependencies.mjs`: он проверяет версии CLI/client, generated client и отсутствие Jest, ts-jest, Handlebars, `@nestjs/cli` и прямых dev-only пакетов.
- Точное локальное воспроизведение production install по lock-файлу прошло: 298 пакетов, 225 верхнеуровневых каталогов; Prisma CLI/client `7.4.0`; Jest, ts-jest, Handlebars и `@nestjs/cli` физически отсутствуют; generated client импортируется.
- Реализован восстанавливаемый upload lifecycle: metadata и квоты сначала резервируются транзакционно, обработанный файл пишется асинхронно во внутренний temp с `wx`, затем атомарно переименовывается; ошибка живого процесса удаляет temp и компенсирует резерв.
- Перед открытием HTTP-сервера запускается fail-closed reconciliation. Она удаляет собственные temp-файлы, canonical orphan/partial/symlink entries, удаляет metadata без точного regular file совпадающего размера и заново рассчитывает все пользовательские и глобальный счётчики. Повторный запуск идемпотентен.
- Reconciliation и удаление работают только со строгими UUID WebP/temp именами и resolved путями непосредственно внутри `UPLOAD_DIR`, используют `lstat` и не следуют symlink. Произвольное имя или повреждённый путь из БД не становится целью файловой операции.
- Удаление пользователя теперь под row lock удаляет его проверенные физические uploads, затем в той же DB-транзакции удаляет пользователя/cascade metadata и уменьшает общий счётчик. При ошибке ФС операция явно возвращает `503`, владелец и metadata сохраняются; возможное частичное физическое удаление исправляет следующая reconciliation.
- Добавлены регрессии на повторные ссылки, общий image/output budget, ошибки чтения, отключённые детали, snapshot boundaries, urlencoded limits, metadata без файла, orphan, temp, неверные counters, traversal, symlink, идемпотентность reconciliation, успешное и аварийное удаление пользователя и production dependency graph.

## Что не сделано и почему

- Не выполнена реальная сборка Linux Alpine image: установленный Docker CLI не смог подключиться к `dockerDesktopLinuxEngine`, поэтому результат не выдумывался. Точный `docker build --no-cache --target runner` оставлен обязательным T-006 gate.
- Не выполнены реальные PostgreSQL/two-tenant и browser-level проверки print/PDF/offline HTML: локальный PostgreSQL runtime и рабочий Linux Docker daemon недоступны. Разрешённый задачей точный сценарий зафиксирован в `docs/tech.md` как обязательный T-006 gate.
- Не исправлялись seed/bootstrap, JWT/session, trust proxy/rate limit, внешние timeout/логи/SMS и срок публичной ссылки: это явно вне границ T-004.

## Технические решения

- Для КП выбран bounded cache на одну генерацию: `Set` дедуплицирует URL до I/O, `Map` связывает URL с коротким ID, а один объект data URI в inline script разделяет payload между всеми DOM-ссылками. В отличие от повторного `src=data:...`, число ссылок больше не умножает base64; последовательный async I/O ограничивает одновременные buffers и не блокирует event loop. Поведение сверено с [Node.js File system promises API](https://nodejs.org/api/fs.html).
- Бюджет 6 MiB raw images даёт максимум около 8 MiB base64 плюс ограниченную разметку; независимый предел 10 MiB проверяет фактический UTF-8 ответ. Для VPS 2 GiB это конечная и тестируемая граница, при этом несколько нормализованных до 500 px WebP полностью помещаются.
- Нечитаемое или не помещающееся изображение деградирует до отсутствующего изображения, а не ломает всё КП. Исключение оставлено только для превышения общего HTML budget, потому что такой ответ уже нельзя безопасно формировать/отдавать.
- Для файла применена схема reserve → temp write → rename с startup reconciliation. DB и файловую систему нельзя объединить одной ACID-транзакцией; поэтому выбран журналируемый через metadata восстанавливаемый протокол с детерминированной сверкой. Canonical names, `path.resolve`/`path.dirname` и `lstat` закрывают traversal и symlink-following.
- Docker production graph строится новым `npm ci --omit=dev` по lock-файлу, а не `npm prune` плюс незакреплённый `npm install`. Это соответствует [npm ci/omit semantics](https://docs.npmjs.com/cli/commands/npm-ci/) и [Docker multi-stage builds](https://docs.docker.com/build/building/multi-stage/).
- Prisma CLI сохранён в production dependencies, потому что контейнер выполняет миграции до старта; client и CLI закреплены одной версией и проверяются внутри image build. Решение сверено с [Prisma `migrate deploy`](https://docs.prisma.io/docs/cli/v7/migrate/deploy) и [официальным deployment guidance](https://docs.prisma.io/docs/orm/prisma-client/deployment/deploy-migrations-from-a-local-environment). Вынос миграций в отдельный непубличный service не потребовался.
- `npm audit --omit=dev` backend сообщает 17 findings: 1 low, 6 moderate, 10 high, critical нет. Все high находятся в необходимой закреплённой Prisma CLI цепочке (`@prisma/config`, `@prisma/dev`, Hono/@hono-node-server/Lodash, mysql2) и не образуют публично достижимый путь: приложение их не импортирует, Prisma CLI читает доверенные committed config/migrations до старта Nest и не открывает этот HTTP server. Runtime low `body-parser` неприменим к валидируемому положительному limit; `qs` ограничен 2 MiB и 1000 параметров и покрыт e2e. Обновление Prisma требует отдельной совместимой dependency-задачи; `audit fix --force` не применялся.
- Полный backend audit содержит 67 findings, включая 1 critical в dev-only Handlebars graph. Проверка фактического production tree доказывает отсутствие Handlebars и прочих build/test dependencies в runner graph, поэтому применимого runtime critical нет.

## Допущения

- Текущий deployment запускает одну backend replica во время startup reconciliation, как задано существующим Compose. Координация одновременного старта нескольких writers вне границ задачи.
- `UPLOAD_DIR` является выделенным persistent volume приложения. Неканонические файлы reconciliation намеренно не удаляет: безопаснее сигнализировать их отдельно, чем считать пользовательские/служебные данные мусором.
- Исходная production среда соответствует условию задачи: чистая PostgreSQL и пустой uploads. Поведение на искусственно повреждённых состояниях покрыто unit-тестами и дополнительно внесено в T-006 gate.

## Безопасность

- Пользовательский/saved ввод ограничен на сервере до чтения файлов и до выдачи ответа; frontend-лимиты не используются как защита.
- Один локальный файл читается один раз, общий raw budget и конечный HTML budget ограничивают CPU/heap/response amplification; I/O асинхронный.
- Сохранены контекстное HTML/attribute/inline-script экранирование, URL allowlist, CSP `sandbox/default-src 'none'` и iframe без `allow-same-origin`.
- Все upload filename/path повторно валидируются перед файловой операцией. Reconciliation не следует symlink, не удаляет произвольные имена и идемпотентно восстанавливает metadata/counters/files.
- Ошибка удаления файла не маскируется успешным удалением владельца: возвращается `503`, DB-транзакция откатывается, последующая reconciliation восстанавливает частичный результат.
- SQL row lock построен через `Prisma.sql` с параметром, без строковой склейки. Tenant-проверки существующих endpoints не ослаблены.
- Dependency graph воспроизводится по lock-файлу; версии Prisma точные и совместимые; финальный tree автоматически отвергает dev/test пакеты. Секреты и production-системы не использовались, на VPS подключений не было.
