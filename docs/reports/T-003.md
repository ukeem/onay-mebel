# Отчёт T-003: Независимо проверить исправления T-002

**Статус:** готово

## Что сделано

### Критично

1. Публичная генерация КП допускает многократное синхронное чтение и base64-встраивание одного локального изображения без общего лимита результата и без дедупликации.
   - **Где:** `backend/src/calculations/public-proposal.controller.ts:20-29`, `backend/src/calculations/calculations.service.ts:932-955`, `backend/src/calculations/calculations.service.ts:2801-2835`, `backend/src/calculations/dto/snapshot-limits.ts:3-8`.
   - **Воспроизводимый сценарий:** авторизованный пользователь сохраняет в допустимом snapshot много деталей с одной и той же канонической ссылкой `/uploads/<file>.webp`, после чего запрашивает публичный `GET /api/public/proposal/:id`. Каждая ссылка отдельно вызывает `statSync`, `readFileSync` и преобразование файла до 5 МиБ в base64. Проверочный запуск на допустимом snapshot из 20 ссылок и файле 1 МиБ создал HTML размером 27 994 331 байт и занял около 68 МиБ heap; лимит массива разрешает 200 элементов, то есть тот же вход масштабируется примерно до 280 МиБ HTML для файла 1 МиБ. Лимит snapshot ограничивает вход, но не развёрнутый HTML.
   - **Последствие:** один пользователь может создавать ответы в сотни мегабайт, а параллельными публичными запросами исчерпать память VPS 2 ГБ и остановить основной сервис. При более крупном допустимом локальном изображении усиление ещё выше. Заявленный риск конечных лимитов ресурсов закрыт не полностью.

### Важно

1. Финальный backend image фактически снова получает dev-граф и непредсказуемую версию Prisma CLI.
   - **Где:** `backend/Dockerfile:19-21`, `backend/Dockerfile:30-32`; ошибочное утверждение об отсутствии Jest/dev-графа — `docs/reports/T-002.md:39` и `docs/tech.md:118`.
   - **Воспроизводимый сценарий:** после чистого `npm ci` команда Dockerfile `npm prune --omit=dev && npm install --no-save prisma` выполняется в builder без `NODE_ENV=production`. Локальное точное повторение установило неприкреплённый `prisma@7.10.1` поверх lock-графа `@prisma/client@7.4.0` и вернуло в физический `node_modules` `jest@30.2.0`, `ts-jest@29.4.6`, `@nestjs/cli` и `handlebars@4.7.8`. Число верхнеуровневых каталогов выросло с 253 после prune до 578 после install. `--no-save` запрещает запись в manifests, но не включает production-only установку; исключение dev-зависимостей зависит от `--omit=dev`/`NODE_ENV=production` ([npm install](https://docs.npmjs.com/cli/v11/commands/npm-install/)).
   - **Последствие:** содержимое production image не воспроизводится по lock-файлу и существенно расширяет attack surface. В образ физически попадает `handlebars@4.7.8`, затронутый critical advisory [GHSA-p8wg-vrv2-v86f](https://github.com/advisories/GHSA-p8wg-vrv2-v86f). Прямой достижимый RCE через HTTP не подтверждён: пакет пришёл через `ts-jest` и runtime-код приложения его не вызывает. Однако lock-only audit не видит фактический граф образа, а Prisma CLI может обновиться несовместимо с клиентом. Prisma рекомендует выполнять `migrate deploy` в CI/CD либо осознанно включать CLI в production dependencies ([официальная документация Prisma](https://docs.prisma.io/docs/orm/prisma-client/deployment/deploy-database-changes-with-prisma-migrate)).

2. Учёт uploads не имеет долговременной сверки БД с файловой системой и ломается на границе сбоя процесса и при удалении пользователя.
   - **Где:** `backend/src/uploads/uploads.service.ts:110-129`, `backend/src/uploads/uploads.service.ts:132-150`, `backend/src/users/users.service.ts:220-235`, `backend/prisma/schema.prisma:99-109`.
   - **Воспроизводимые сценарии:**
     - процесс завершается после `reserveStorage()` и фиксации транзакции, но до `writeFile()` либо до возврата URL; in-process компенсация из `catch` уже не выполняется, а API для списка/сверки потерянных записей нет;
     - администратор удаляет пользователя: FK `Upload.owner` с `onDelete: Cascade` удаляет строки Upload, но `users.service.ts` не удаляет физические файлы и не уменьшает singleton-счётчик `UploadStorage.usedBytes`.
   - **Последствие:** возможны потерянные файлы, отсутствующие файлы при существующей metadata и необратимо завышенный общий/пользовательский учёт. Повторение сбоев или удалений пользователей способно исчерпать диск либо глобальную квоту 1 ГиБ при фактически свободном хранилище. Гонки обычных конкурентных резервирований закрыты условными атомарными update, но crash consistency не закрыта.

3. Security-тесты T-002 перечисляют восемь component endpoints, но не доказывают заявленные границы на реальной persistence-семантике и не покрывают несколько критичных отрицательных путей.
   - **Где:** `backend/src/products/products.security.spec.ts:14-35` и `:38-111`, `backend/test/product-limits.e2e-spec.ts:14-29`, `backend/src/uploads/uploads.service.spec.ts`, `backend/test/upload-limits.e2e-spec.ts:20-29`, `backend/src/calculations/calculations.security.spec.ts:19-72`, `backend/test/request-limits.e2e-spec.ts`.
   - **Воспроизводимый сценарий:** component security test подставляет hand-written Prisma delegates, которые для всех восьми типов просто возвращают пустые массивы; HTTP e2e полностью мокирует `ProductsService`. Поэтому тест проходит и при неверной реальной Prisma-фильтрации, нарушенной FK/transaction семантике или partial write. Аналогично upload e2e мокирует `UploadsService`, а тест КП проверяет строки результата, но не исполнение в браузерном iframe/CSP-контексте.
   - **Пробелы:** нет интеграционного сценария с двумя владельцами для всех восьми типов; нет проверки rollback/partial write и одинакового поведения чужого/неизвестного ID на БД; нет гонки global quota, crash/compensation failure, рассинхронизации БД/ФС и удаления пользователя; нет browser-level проверки iframe, `postMessage`, Blob/download/print; snapshot-тесты не перебирают byte/node/object-key/NaN границы; request e2e не проверяет urlencoded `parameterLimit` и согласование с nginx.
   - **Последствие:** зелёный набор не является достаточным regression gate для наиболее рискованных исправлений. Это не замечание об отсутствии локального PostgreSQL/Docker у T-002: требуются корректные интеграционные/браузерные тесты, а реальный Linux/PostgreSQL deployment gate по-прежнему остаётся в T-006.

### Желательно

Нет находок.

Дополнительно подтверждено статическим анализом:

- все восемь массовых component endpoints проверяют owner scope продукта и component IDs до транзакции, а записи/удаления выполняют атомарно внутри транзакции; чужие и неизвестные ID получают одинаковый `404`, дубликаты отклоняются;
- shared material/hardware доступны, custom material/hardware ограничены текущим владельцем и enabled-записью пользовательского каталога;
- upload flow ограничивает multipart до декодирования, проверяет MIME/magic/decode, выдаёт UUID `.webp`, пишет с `wx`, авторизует удаление владельцем и не позволяет path traversal через публичный URL;
- обычные конкурентные user/global quota reservations используют условные атомарные обновления BigInt-счётчиков; ошибки записи компенсируются, пока процесс жив;
- HTML-, attribute-, URL- и JSON-контексты КП экранированы; локальные изображения допускаются только по каноническому `/uploads/...`; CSP и iframe sandbox ограничивают документ, русские и казахские строки сохраняются;
- JSON 2 МиБ, urlencoded 2 МиБ/1000 параметров, nginx 6 МиБ, multipart 5 МиБ и snapshot byte/depth/array/object/string/node/finite-number limits согласованы по назначению и возвращают ожидаемые `400`/`413`;
- Prisma schema и 25 миграций статически воспроизводимы от пустой базы; ownership FK/index/unique и BigInt-поля квот согласованы;
- frontend `picomatch@4.0.3` остаётся high в lock-графе ([GHSA-c2c7-rcm5-vvqj](https://github.com/advisories/GHSA-c2c7-rcm5-vvqj), также [GHSA-3v7f-55p6-f55p](https://github.com/advisories/GHSA-3v7f-55p6-f55p)), но отсутствует в `.next/standalone`; приложение не принимает пользовательские glob patterns, поэтому runtime-достижимость не подтверждена;
- секретов и неожиданных изменений вне scope T-002 не найдено.

## Что не сделано и почему

- Код, конфигурация и существующие документы не менялись: задача имеет пометку `[review]`, исправления должны выполняться отдельной задачей.
- Реальная миграция PostgreSQL и запуск Linux/Docker image не выполнялись. По условию задачи это deployment gate T-006 и само по себе не является находкой; schema/migrations и Docker-команды проверены статически и локальным воспроизведением npm-графа.
- К production-секретам и VPS подключений не было.

## Технические решения

- Проверен фактический diff `959e123` и `8657766` относительно родителя `b1bd04c`, а не только отчёт T-002.
- Для tenant isolation прослежены controller → DTO/pipe → service → Prisma transaction для каждого из восьми типов: sections, partitions, shelves, facades, drawers, false facades, countertops и extras.
- Для uploads отдельно прослежены ранние HTTP limits, decode/normalization, reservation transactions, filesystem operations, delete, FK cascade и публичная static-раздача. Crash-сценарии оценивались по границам фиксации БД и ФС.
- Для КП проверены HTML text/attribute/script/URL contexts, JSON embedding, локальные data URI, заголовки CSP, iframe sandbox, `postMessage`, Blob/download/print. Ресурсное усиление дополнительно воспроизведено динамически без записи временных файлов.
- Аудиты выполнены по каждому lock-файлу полностью и с `--omit=dev`; advisory сверены с фактической достижимостью. Отдельно воспроизведены ровно npm-команды backend Dockerfile, поскольку `npm audit --package-lock-only` не отражает неприкреплённый install-time граф.
- Новые библиотеки не добавлялись и auto-fix не запускался.

## Допущения

- Production начинается с чистой PostgreSQL и пустого uploads, как указано в задаче; исторические данные и старые произвольные имена файлов не оценивались.
- Пользователь с обычной авторизацией считается потенциально недоверенным и может многократно читать публичную ссылку собственного КП.
- Проверка воспроизводимости миграций является статической до T-006; успешный реальный `migrate deploy` не заявляется.

## Безопасность

- Проверены разграничение tenant-данных, server-side authorization и неразличимость чужих/неизвестных идентификаторов для всех восьми component endpoints.
- Проверены пользовательские файлы: размер, MIME/magic/decode, нормализация, canonical path, ownership, квоты, конкурентные обновления, компенсация ошибок, public read, traversal и symlink/path surface.
- Проверены все контексты вставки пользовательских данных в КП, CSP/sandbox и клиентские каналы взаимодействия.
- Проверены входные лимиты и ошибочные значения, Prisma ownership/FK/index/unique/BigInt, dependency advisories и фактические runtime-графы.
- Найденные незакрытые риски: критическое усиление памяти при генерации КП; отсутствие durable reconciliation uploads; невоспроизводимый и расширенный backend runtime graph; недостаточная интеграционная доказательность security-тестов.

## Вопросы и предложения мозгу

- Не принимать T-002 как полностью закрывшую production-риски до отдельного исправления критического output/memory amplification в КП.
- До деплоя исправить backend Docker dependency graph и добавить проверку содержимого финального image, а также durable reconciliation/cleanup uploads.
- Добавить интеграционный regression gate с двумя tenants и реальной PostgreSQL-семантикой для восьми endpoints, конкурентных квот и rollback, плюс browser-level тест публичного КП.
- T-006 по-прежнему должна выполнить реальный Linux/PostgreSQL/Docker deployment gate; эта находка не заменяет и не дублирует T-006.
