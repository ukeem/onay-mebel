# Отчёт T-002: Закрыть критические уязвимости до production

**Статус:** готово

## Что сделано

- Закрыта tenant isolation для всех восьми наборов компонентов изделия: sections, partitions, shelves, facades, drawers, false facades, countertops и extras. Product/room и переданные component ID проверяются сервером в scope владельца до транзакции; чужой и отсутствующий ID дают одинаковый 404, повторяющиеся ID отклоняются и не превращаются в новые записи.
- Material/hardware в компонентах принимаются только при наличии enabled-связи `UserMaterial`/`UserHardware` текущего пользователя. Общая позиция (`userId=null`) и собственная custom-позиция продолжают работать; чужая custom-позиция отклоняется.
- Добавлена модель ownership uploads: `Upload`, `UploadStorage`, `User.uploadBytes` и миграция `20261021070000_secure_upload_ownership`. Удаление разрешено только владельцу канонического `/uploads/<uuid>.webp`; чужой и неизвестный файл дают одинаковый 404, traversal/неверный URL — 400. Отсутствующий на диске свой файл согласованно удаляет запись и квоту, прочая ошибка файловой системы не стирает метаданные. Публичное чтение `/uploads/` для КП сохранено.
- Upload обрабатывается до записи на диск: Multer ограничивает один файл и 5 MiB, запрещает дополнительные fields/parts, затем проверяются extension, MIME и magic bytes. Sharp ограничивает вход 13 MP, отключает animation, поворачивает и преобразует изображение в WebP шириной до 500 px. Резерв квоты и метаданные создаются транзакционно; ошибка записи откатывает резерв. Default-квоты — 100 MiB на пользователя и 1 GiB суммарно.
- Защищена генерация КП во всех контекстах: HTML и attributes экранируются, inline JSON кодирует `<`, `>`, `&`, U+2028/U+2029, contact URL строится по allowlist типа, изображение принимается только из канонического локального uploads и встраивается как ограниченный data URI. Payload с `</script>`, event handlers, атрибутами и `javascript:` не исполняется.
- Ответ КП и сам скачиваемый/Blob HTML получили CSP с `default-src 'none'` и sandbox. Публичный и внутренний iframe используют `sandbox="allow-scripts allow-modals"` без `allow-same-origin`; переключение тарифа идёт через `postMessage` с фиксированным allowlist. Русский/казахский текст, локальный WebP-логотип, печать и скачивание HTML сохранены.
- Встроенный Nest body parser заменён явным Express parser до auth: JSON/urlencoded не более 2 MiB и 1000 параметров. Ошибки синтаксиса дают 400, превышение — 413. Snapshot ограничен 1.5 MiB, depth 12, 200 элементов массива/ключей объекта, строкой 5000, 25 000 узлов и конечными числами. DTO получили конечные границы строк, чисел и массивов; каждый component endpoint отсекает более 100 элементов до поэлементного parsing.
- nginx согласован с backend: `client_max_body_size 6m`, короткий body timeout и ограниченный request buffer. `.env.example` и Compose содержат явные JSON/upload limits.
- Точечно обновлены применимые runtime-зависимости и lock-файлы: Next 16.4.2, Nest core/platform 11.1.18, Multer 2.4.0, sharp 0.35.5, Axios 1.20.0, Socket.IO 4.8.4, compression 1.8.2, Joi 18.2.9 и совместимые overrides для уязвимых транзитивных пакетов. `audit fix --force` не применялся.
- Устранены ESLint errors. Для Next 16.4.2 build закреплён официальный `next build --webpack`: локальный Turbopack дважды завершал PostCSS child process внутренней ошибкой, а Webpack build воспроизводимо проходит. React-изменения проверены на корректность hooks, освобождение Blob URL и отмену fetch.
- Добавлены unit/security и e2e-регрессии на все перечисленные атаки и превышения лимитов.

## Что не сделано и почему

- Не выполнен реальный `prisma migrate deploy` на чистой PostgreSQL и повторный no-op deploy: Docker CLI установлен, но daemon недоступен (`npipe:////./pipe/dockerDesktopLinuxEngine` отсутствует), локальный `psql` не установлен. Schema, Prisma Client, история из 25 миграций и полный empty-to-schema SQL diff проверены без выдуманного результата.
- Обязательный gate T-006: на чистой PostgreSQL 16 выполнить все 25 миграций командой `npx prisma migrate deploy`, повторить команду и получить отсутствие pending migrations, проверить `_prisma_migrations`, `User.uploadBytes`, `Upload`, `UploadStorage`, затем собрать Alpine Docker image и пройти upload/delete/public-proposal smoke под production env и resource limits.
- Не исправлялись seed/bootstrap, JWT role/session revocation, trust proxy/rate limit, внешние timeout, логи/SMS reset, backup, timezone, срок публичной ссылки и другие явно исключённые из T-002 вопросы.

## Технические решения

- Ownership проверяется scoped-запросом к БД, а не доверенным client ID. Предварительная проверка всего массива до delete/upsert предотвращает частичную запись и замену чужого ID созданием новой строки.
- Для файлов использованы существующие Prisma и sharp, без нового хранилища. Счётчики квот атомарно обновляются условными `updateMany`; физическая запись имеет `wx`, а компенсация удаляет резерв при ошибке. Чистая БД и пустой uploads соответствуют исходным условиям задачи.
- HTML не очищается эвристически: каждый контекст кодируется отдельно, URL формируются из allowlist, iframe остаётся opaque-origin. Решение основано на [MDN iframe sandbox](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe); сочетание `allow-scripts` и `allow-same-origin` отвергнуто как снимающее изоляцию.
- Ранние лимиты выбраны по [Nest file upload](https://docs.nestjs.com/techniques/file-upload), [Multer 2.4.0 changelog](https://github.com/expressjs/multer/blob/main/CHANGELOG.md) и [Express body-parser](https://expressjs.com/en/resources/middleware/body-parser/). nginx принимает небольшой multipart overhead над backend 5 MiB, но не позволяет обойти backend-проверку.
- Миграция оформлена SQL-файлом Prisma; production-команда сверена с [Prisma 7 migrate deploy](https://www.prisma.io/docs/cli/v7/migrate/deploy).
- Webpack-флаг является поддерживаемым CLI Next 16: [Next CLI](https://nextjs.org/docs/app/api-reference/cli/next). Он выбран вместо непредсказуемого локального Turbopack fallback внутри CI/Docker.
- Обновления зависимостей ограничены публично достижимыми рисками: [Next RSC advisory](https://github.com/vercel/next.js/security/advisories/GHSA-h25m-26qc-wcjf), [sharp advisory](https://github.com/lovell/sharp/security/advisories/GHSA-wq5f-xc86-pv6w), [Axios advisory](https://github.com/advisories/GHSA-542g-h47m-68v8) и [Socket.IO security history](https://github.com/socketio/socket.io/blob/main/SECURITY.md). Несовместимое массовое обновление Prisma/Jest/ESLint не делалось.

## Допущения

- Production стартует с чистой PostgreSQL и пустым uploads, как задано; миграция не пытается восстановить ownership исторических файлов.
- 5 MiB на исходное изображение, 13 MP decode, 100 MiB на пользователя, 1 GiB суммарно, JSON 2 MiB и snapshot 1.5 MiB приняты как безопасные начальные пределы для VPS 2 CPU/2 GiB. Они настраиваются только в заданных верхних границах и требуют наблюдения после запуска.
- Публичный `/uploads/` остаётся намеренно читаемым: секретность обеспечивается UUID URL, а право удаления — записью владельца. Это сохраняет основной сценарий КП, но не превращает URL изображения в приватный ACL.
- Обычный логотип хранится через новый upload endpoint в каноническом WebP; произвольные внешние/data/javascript URL в КП не поддерживаются.

## Как проверить

1. Установить зависимости: в корне и backend `npm ci`, во frontend `npm ci --legacy-peer-deps`.
2. Backend: `npx prisma generate`, `npx prisma validate`, `npm test -- --runInBand`, затем с фиктивными test env `npm run test:e2e -- --runInBand --forceExit`, `npx tsc --noEmit`, `npm run build`, `npm run lint`.
3. Frontend: `npx tsc --noEmit`, `npm run lint`, `npm run build`.
4. В каждом из root/backend/frontend выполнить отдельно `npm audit --json` и `npm audit --omit=dev --json`.
5. С production-подобными непубличными test env выполнить `docker compose config --quiet`.
6. На доступной чистой PostgreSQL 16 выполнить обязательный gate T-006 из раздела «Что не сделано и почему».
7. Ручной smoke: два пользователя; подстановка каждого из восьми чужих component ID и чужого product ID; чужие custom material/hardware; загрузка/удаление своего и чужого файла; публичное изображение; XSS payload в названии/описании/контакте/изображении; печать и скачивание КП; JSON/multipart/quota oversize.

## Безопасность

- Ввод: ранние nginx/Express/Multer limits, DTO и рекурсивный snapshot validator; oversize даёт 400/413 без частичных файлов/данных.
- Авторизация: серверный owner scope для product/room/всех восьми компонентов и uploads; чужое неотличимо от отсутствующего; catalog availability проверяется сервером.
- Файлы: формат проверяется по содержимому, decode ограничен, имена генерируются UUID, traversal исключён, квоты атомарны, рассинхронизация БД/ФС обработана.
- HTML: contextual escaping, URL allowlist, безопасная сериализация JSON, CSP и opaque-origin sandbox; dangerous payload покрыт тестами.
- БД/команды: Prisma parameterized API; shell-команды из пользовательского ввода не строятся; schema-изменение имеет миграцию.
- Секреты/логи: реальные production-секреты не использовались и не добавлены; тестовые env фиктивны; `.env` не отслеживается.
- Зависимости: применимые public runtime advisories закрыты точечно; оставшиеся high/critical классифицированы выше по reachability и advisory. Audit является снимком на 2026-10-22 и должен повторяться перед каждым production release.
